2. DECISIONS AND WHY
--------------------

2.1 Unit tests never call an LLM. Numbers must come from code, not from the
    model; tests that call a model are slow, cost money and change between
    runs. The app accepts replacements for its LLM parts (fake extractor,
    fake investigator, DeterministicFakeEmbedding), so the real code around
    the model is tested for free.

2.2 Integration tests are behind a pytest marker and compare every store
    (Postgres, pgvector, ChromaDB, Neo4j) with the source CSV files. This
    catches lost rows and duplicates; a plain `pytest` still runs without
    Docker.

2.3 Known gaps are marked xfail(strict=True), not deleted. The suite stays
    green, the gap stays documented, and the suite fails as soon as the gap
    is fixed, so the marker cannot be forgotten.

2.4 Fewer, meaningful tests. Each test checks one rule with the input that
    would actually break it. Reviews removed repeated cases (e.g. 51 -> 30
    tests) without losing coverage. Defenses were broken on purpose to
    confirm the tests fail (one test was found not to be specific and was
    fixed).

2.5 The app's own services are tested, not only helper functions. The golden
    numbers come out of two independent implementations: our helpers and
    services/impact.py + services/recovery.py.

2.6 Retrieval benchmark: 31 hand-written questions, every expected document
    checked by hand. Large enough to separate the modes, small enough to
    verify. "incident HC-026" was replaced by "HC-012", because the hybrid
    search contains a rule designed around HC-026 (avoid measuring the case
    the code was tuned on).

2.7 The 105 evaluation cases are held out (CONTRIBUTING rule 6): they are only
    measured, never used in tests or for tuning. Numbers and ids are checked
    by code. Behaviour written as text ("refuse: quarantined") is checked by
    an LLM judge that also writes its reason. Each run is one LangSmith
    experiment, so before/after runs can be compared.

2.8 Two layers plus manual tests. "The system did the right thing" (plans,
    approvals, POs - checked by code) and "the assistant said the right
    thing" (LLM judge) fail independently, so both are measured. Manual tests
    add what neither sees: the UI, roles across logins, a real restart. They
    also caught an error the judge accepted (E2 in the manual plan).


3. FINDINGS
-----------

Serious (affect correctness or the demo)

3.1 A new case ignores actions executed by earlier cases. Two cases moved the
    same 800 units out of W-HUB and expedited PO-2026-9002 twice.      #57
3.2 A case that fails at intake (LLM error) stays "intake" for good, and the
    chat stays bound to it: the next message fails with KeyError.       #56
3.3 The follow-up assistant states wrong facts: above EUR 75,000 "needs PM +
    FC" (tool says finance director); Delta and Atlas "disconnected"
    (they share Veltro); offers to use the superseded 10-day contract.  #54
3.4 The recommended plan changes between identical runs (EUR 30,378 once,
    EUR 39,218 twice), and plan_full_cover relies on Delta despite a high
    alert on its upstream Veltro. Conflict resolution also changed (Helios
    capacity 4,000 vs 1,500).                                           #59
3.5 Intake rejects components that exist but are used in no product
    (7 of 64 extraction cases). The fix must still ask when a component
    does not exist, or the ambiguity cases break.                       #53

Medium

3.6 Supplier names with a suffix ("Orion Supply Ltd") are not resolved;
    22 such variants in the data.                                       #21
3.7 A finance controller can open a case; the full investigation runs and is
    refused only at "submit for approval".                              #58
3.8 No defense of the app's own against "print your system prompt": it was
    stopped by the Azure content filter, and the user is told "the model is
    unreachable - ask again", which is misleading.
3.9 The golden message itself is reported as a prompt injection (false
    positive in the user-message scan).
3.10 No user has the finance_director role, so a EUR 90,000 plan can be
    discussed but never approved. IdentityService.require_can_approve_as
    works and is tested but is not called anywhere.

Retrieval

3.11 Embeddings cannot tell identifiers apart (HC-026 vs HC-029) and keyword
    search misses paraphrases. Hybrid finds the expected document in the top
    5 for every question; weakest result: the Delta offer e-mail ranks 4th.
    pgvector and ChromaDB give identical results (same vectors).

Fixed by the team after review: the injection scan now also covers the
user's message, with two independent detectors (LLM and pattern scan).


4. NOT TESTED - AND HOW IT COULD BE DONE
----------------------------------------

4.1 Re-running the document ingestion. It calls the embedding API on every
    run. ingest() accepts an Embeddings object and temporary table names, so
    a test could run it twice with DeterministicFakeEmbedding and check the
    chunk count stays 272.

4.2 Graph mode in the benchmark. mode="graph" is not wired in
    build_postgres_retrieval; once it is, add "graph" to the benchmark modes.


5. LIMITATIONS
--------------

- 31 benchmark questions show a trend, not certainty: one question moves
  recall by about 3 points.
- Each evaluation ran once. The LLM gives different answers between runs
  (3.4), so a single score can move; repeated runs would give a range.
- The LLM judge is lenient: it passed answers with the right conclusion and
  the wrong reason (EV-0083, EV-0097).
- Manual tests were run once, by one person, on one PC.
- Nothing in this work was tuned on the held-out evaluation cases.
